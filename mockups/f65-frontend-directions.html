Frontends for the F65 controller

Today f65 is a 436-line Swift CLI that talks to the AULA F65 over IOKit HID: it reads and writes lighting and both key layers, and backs everything up before each write. Below is what a frontend has to surface, four ways to build it, and the motion each one needs. Lighting values are loaded from your latest backup (f65-20261117-023015.txt).

Drag to turn the board. Click a key, or type on your F65, to press it; Ripples, Reaction, Shadow and Flash away respond to presses. The model follows the F65's 67-key layout and 325 × 116 mm footprint. Effects are approximations drawn in the browser, not read from the keyboard.

What the codebase can drive

Each protocol command maps to a screen. Only the confirmed read/write paths should ship as editable controls; the rest show up as read-only or reserved space so the layout does not change when they land.

Before any of these can ship

Split out an F65Kit packageMove the F65 class, key tables and backup code out of the CLI file so the app and CLI share one library.
No more exit() and print()Commands call exit on failure. A UI needs thrown errors with messages it can show next to the control.
Progress from write()Each 14-byte packet is acked. Exposing a per-packet callback drives the real progress bar (10 packets for lighting, 36 for a key layer).
Device actor + hot-plugRun HID I/O on its own actor/run loop, register a matching callback for plug/unplug, and publish unsolicited 0A status reports as live state.

Recommendation

  1. Build the Mac app (A) and the menu bar extra (B) as one SwiftUI target on top of an F65Kit package. They share state, and B covers the daily use while A handles remapping.
  2. Keep the CLI as a thin client of F65Kit. The terminal UI (D) is optional; it is cheap once the package exists.
  3. Treat the browser version (C) as a later share-with-others project, since it means porting the protocol to TypeScript.
